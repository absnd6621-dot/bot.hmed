# تشغيل البوت على VPS وتحديثه تلقائياً

هذا الإعداد لخادم Linux دائم التشغيل مع Docker وDocker Compose v2 وGit، وليس لاستضافة مواقع مشتركة. يلزم أيضاً صلاحية تشغيل Docker للمستخدم الناشر. يعمل البوت بنسخة واحدة فقط (Telegram polling)، وPostgreSQL وRedis على الخادم نفسه. قبل تشغيل نسخة أخرى أوقف القديمة.

## أول تشغيل

1. ادمج فرع التعديلات في `main` على GitHub. اجعل المستودع خاصاً إن كان يحتوي على معلومات لا تريد نشرها.
2. على الخادم، استنسخ المستودع إلى المسار الثابت التالي بحساب يستطيع تشغيل Docker:

   ```bash
   sudo mkdir -p /opt/bot-hmed
   sudo chown "$USER":"$USER" /opt/bot-hmed
   git clone -b main رابط-المستودع /opt/bot-hmed
   cd /opt/bot-hmed
   cp .env.example .env
   chmod 600 .env
   ```

   للمستودع الخاص، اضبط مفتاح GitHub deploy key للقراءة على الخادم؛ يجب أن ينجح `git fetch origin main` دون مطالبة بكلمة مرور. لا تضع رمز الوصول في رابط المستودع.
3. عدّل `.env` على الخادم فقط: ضع `BOT_TOKEN` من BotFather و`ADMIN_IDS` أرقام حسابات الأدمن و`ADMIN_NOTIFY_CHAT_ID` رقم محادثة الإشعارات. عيّن `POSTGRES_PASSWORD` إلى قيمة عشوائية سداسية طويلة (مثلاً `openssl rand -hex 32`) قبل أول تشغيل. لا تغيّر كلمة مرور PostgreSQL في الملف وحده بعد إنشاء قاعدة البيانات؛ تغييرها يتطلب تعديلها داخل PostgreSQL أيضاً.
4. عيّن مفتاحي `INVENTORY_ENCRYPTION_KEY` و`BACKUP_ENCRYPTION_KEY` إذا كنت ستستخدم المخزون أو النسخ الاحتياطي. أنشئ مفتاح Fernet لكل واحد مثلاً بـ `python3 -c 'import base64,os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())'`. احتفظ بهما بأمان خارج الخادم؛ تغييرهما قد يمنع قراءة البيانات المشفرة. اضبط مزودي الدفع والمفاتيح الاختيارية حسب الحاجة.
5. شغّل `bash deploy/update.sh`، ثم راقب `docker compose ps` و`docker compose logs -f bot api`. اختبر البوت من حساب الأدمن.

الـ API يستمع افتراضياً على `127.0.0.1:8080` فقط. للـ Mini App أو webhooks تحتاج نطاقاً وHTTPS وreverse proxy إلى هذا المنفذ، مع ضبط `WEBAPP_URL` و`ADMIN_WEBAPP_URL` و`PUBLIC_BASE_URL` حسب الاستخدام. لا تنشر المنفذ مباشرة دون إعداد حماية وHTTPS.

## تفعيل التحديث التلقائي

1. أنشئ مفتاح SSH مخصصاً للنشر وأضف المفتاح العام إلى `~/.ssh/authorized_keys` لمستخدم الخادم. هذا المستخدم يحتاج الوصول للمجلد وصلاحية Docker، وهي صلاحية عالية على الخادم.
2. من GitHub ← Settings ← Secrets and variables ← Actions أضف الأسرار: `DEPLOY_HOST` عنوان الخادم، `DEPLOY_USER` مستخدم SSH، `DEPLOY_SSH_KEY` المفتاح الخاص كاملاً، و`DEPLOY_KNOWN_HOSTS` سطر مفتاح المضيف الموثوق لخادم SSH. تحقق من بصمة المضيف من لوحة مزود الاستضافة أو وصول موثوق قبل إضافته؛ لا تثق بمفتاح مأخوذ من الشبكة دون تحقق.
3. كل push إلى `main` سيشغل workflow النشر. يمكن تشغيله يدوياً من Actions على `main`. إن لم تُضبط الأسرار سيتخطى النشر. راجع سجل Actions وسجل الخدمات عند أي خطأ. لا يعد نجاح workflow دليلاً على جاهزية البوت عندما تكون الأسرار ناقصة.

النشر يسحب `main` فقط بتحديث fast-forward ويرفض التعديلات المحلية، ثم يبني الصور وينفذ ترحيلات قاعدة البيانات قبل إعادة تشغيل الخدمات. أي تغييرات على الفرع الحالي لا تصل للاستضافة حتى تُدمج في `main`. لا تضع إعدادات أو ملفات داخل مجلد المشروع إلا `.env` المتجاهل. افحص الترحيلات وخذ نسخة احتياطية قبل التحديث؛ التراجع عن الكود لا يعكس ترحيلات قاعدة البيانات تلقائياً.

## البيانات والنسخ الاحتياطية

Docker volumes تحفظ PostgreSQL وRedis والنسخ المحلية في `/app/backups` عبر إعادة بناء الحاويات؛ لا تستخدم `docker compose down -v` لأنه يحذفها. هذه ليست نسخة احتياطية خارجية: خذ نسخ PostgreSQL مشفرة ومنتظمة إلى مكان منفصل، واختبر استعادتها واحتفظ بمفاتيح التشفير. تغيير `BACKUP_DIR` إلى مسار آخر يتطلب إضافة volume مناسب. راجع إعدادات firewall وتحديثات الخادم دورياً.
